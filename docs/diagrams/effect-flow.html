Effect flow — the core decides, the caller performs
can() answers with a verdict and a list of effects; applyTransition() folds that list into the fields it produces. Effects are interpreted once, in the core — adapters store the result and never switch on an effect type.
Two ways to ask
packages/domain/src/note-machine/machine.ts
can(action, ctx) — the caller knows which of the 10 actions it wants
canTransitionTo(to, ctx) — the caller only learned the destination (a pushed event); the core resolves the edge
Context — everything the rules need
no globals, no clock
status · assignedReviewerId · approvedAt · actor {id, role}
now (ISO, caller-supplied) · reason · mfaVerified · source user asks and must prove it, system was already decided
Pure evaluation — three steps, in order
findTransition(action, from)
Looks up the edge in the 11-row TRANSITIONS table. Missing edge means the action was never legal here.
guard(ctx)
Role, assignment, MFA, non-empty reason, 24h amend window. Returns a sentence on refusal, null to allow.
effects(ctx)
Builds the change as plain data. Reads ctx.now and ctx.actor; performs nothing.
Refused
{ ok: false, action, from, reason }
The reason is written to be read by a human. Web: disabled button plus tooltip — no request is sent. API: 409 transition_rejected carrying the same sentence, because the browser's verdict is only advisory.
Allowed
{ ok: true, action, from, to, effects: TransitionEffect[] }
to is the next status. Everything else that must change travels in effects — five variants, closed union, handed straight to the fold below.
Effect Emitted by Means
assign_reviewer(reviewerId) start_review (from READY_FOR_REVIEW, AMENDED) The actor takes ownership of the review.
release_reviewer return · approve · reject Ownership ends; the note is nobody's until claimed again.
record_approved_at(at) approve Stamps the clock the amend grace window is measured from.
clear_approved_at amend Reopens the note; the old approval no longer stands.
require_new_version resubmit · amend Content must continue on a fresh version row rather than overwrite a signed one — surfaced as a flag, since version rows are storage.
The one place effects are interpreted
applyTransition(state, result)
Folds the effect list over the caller's current lifecycle fields. Exhaustive switch — a sixth effect fails the build here, once, instead of silently in each adapter.
→ { status, assignedReviewerId, approvedAt, requiresNewVersion }
The next state, in the core's own vocabulary: ids, not user objects; a flag, not a version row. Storage is the caller's business.

Web — the optimistic guess
entities/note/lib/transition-patch.ts
Names the reviewer — the only translation it owns: an id becomes a UserRef the cache can render, or waits for the server if it belongs to nobody in hand.
requiresNewVersion is ignored — only the server mints versions; the new revision arrives over the socket.
Detail cache, list caches, and a local review row are patched from one object; the pre-patch snapshot is the rollback.
Same function serves both directions: the action a user clicked, and a status change observed over the socket.
Neither adapter mentions an effect type. They receive the next lifecycle state and are left with the work only they can do — persisting rows, branching versions, hydrating users, painting caches.
